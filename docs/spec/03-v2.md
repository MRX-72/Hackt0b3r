# PART 4: V2 ADDENDUM (ARCHITECTURE, CLI, GUI, PACKETS, MODES, RULES, ALERTS)


This extends Part 3 (Base Specification). Where the two conflict, **this part wins**. Adds: privilege-separated backend, CLI, GUI, Wireshark-style packet view, monitoring modes, a rule engine (detection and enforcement), and Slack/Telegram/Discord alerts.

**Build notes:** Build by priority tier (section 12). Finish every P0 item before touching P1, and every P1 before P2. Anything marked "verify" must be tested on the real machine. Log deviations in `NOTES.md`.

## 1. Scope reality check

The original spec fits a 10-hour hackathon. This addendum does not fit in 10 hours. Tiers:

- **P0 (hackathon core, original spec + this):** daemon/API split, CLI basics, GUI core views, one notification channel, packet list view (lite), monitoring modes (config bundles), dry-run enforcement rules.
- **P1 (strong demo upgrade):** all three notification channels, full packet view (detail pane, hex, follow stream, display filters), detection-rule YAML engine, rule test mode.
- **P2 (post-hackathon roadmap):** two-way approval from chat apps, RBAC, plugins, Linux enforcement adapter, multi-sensor.

Do not trade P0 reliability for P1/P2 features. A flawless P0 demo beats a flaky everything-demo.

## 2. Architecture (privilege separation)

Packet capture needs root. Everything else should not run as root.

```
 ┌───────────────────────────┐        ┌────────────────────────────────┐
 │ ravend (root)          │        │ raven-api (unprivileged)    │
 │  - capture (BPF filter)   │ Unix   │  - FastAPI REST + WebSocket    │
 │  - minimal parse -> flows │ socket │  - detectors, correlation, LLM │
 │  - pcap ring buffer       ├───────►│  - notifications, budget       │
 │  - enforcement helper     │◄───────┤  - serves GUI, auth            │
 │    (pf anchor only)       │ cmds   │                                │
 └───────────────────────────┘        └──────────┬─────────────────────┘
                                                 │ HTTP 127.0.0.1 + token
                                      ┌──────────┴──────────┐
                                      │ raven CLI / GUI  │
                                      └─────────────────────┘
```

- **ravend (root):** does only three things: capture, write pcap ring buffer, apply/remove approved enforcement rules. Keep it small and boring. It exposes a narrow command set over a Unix socket owned by the raven user (mode 0600).
- **raven-api (unprivileged):** all detection logic, storage, LLM, notifications, web server. Never runs as root.
- **Packet parsing is attack surface.** Malformed packets must never crash the daemon. Wrap parsing in try/except, count parse errors, and add a fuzz-style test feeding random bytes to the parser.
- **API binds to 127.0.0.1 by default.** LAN access is an explicit opt-in flag with a visible warning. All API calls require a bearer token generated at first run (stored in a 0600 file). CLI and GUI read that token.
- **Event bus:** an in-process async queue between ingestion, detectors, correlation and notifiers. Apply backpressure: if the queue is full, drop lowest-priority flow events and increment a visible "dropped" counter. Never block capture.

## 3. Backend quality bar

- Config validated with pydantic; invalid config fails fast with a clear message.
- SQLite in WAL mode, schema migrations (simple numbered SQL files), indexes on `(host_mac, ts)`.
- Retention policy: flows N days, alerts M days, pcap ring buffer by size cap. All configurable.
- Structured JSON logging, plus `GET /metrics` style counters (packets/s, flows/s, queue depth, dropped, parse errors, detector latency).
- Detector interface so detectors are pluggable: `class Detector: name; def on_window(self, ctx) -> list[Alert]`.
- Audit log (append-only table) for every state change: rule applied/removed, device label edited, mode changed, notification config changed, who/what triggered it.
- Tests: unit tests for each detector using synthetic flow fixtures, a replay-based end-to-end test, parser fuzz test, rule-engine tests. CI-style `make test`.
- Performance target to measure and report: sustained packets/s on the gateway Mac and CPU use with capture + detection + dashboard running. Report the real number, don't assume.

## 4. CLI (`raven`)

Single entry point, talks to the API. Output is human-readable by default and `--json` for scripting.

```
raven status                      # mode, capture state, counters, health
raven start | stop                # control capture
raven mode list|set <name>        # monitoring modes (section 7)
raven devices [--unknown]         # inventory
raven device label <mac> <type>   # correct a device type
raven incidents [--open] [--top N]
raven incident show <id>          # timeline, evidence, ATT&CK chain
raven alerts [--since 1h]
raven packets live [--filter EXPR]        # terminal packet list (like tshark)
raven packets show <id>                   # decoded layers + hex
raven capture export --since 5m --out x.pcap   # opens in Wireshark
raven rules list|show|test|enable|disable <id>
raven rules add -f rule.yaml
raven enforce list                # pending / active enforcement rules
raven enforce approve <id> [--ttl 30m]
raven enforce revoke <id>
raven notify test <channel>       # slack|telegram|discord
raven notify status
raven replay <file.pcap> [--speed 10]
raven eval run                    # purple-team suite
raven doctor                      # checks interface, permissions, Ollama, DB, channels
```

`raven doctor` is important: it verifies the interface name, sudo/capture permission, daemon reachable, model available, and each notifier's configuration. It should be the first thing a new user runs.

## 5. GUI

Served by the API at `http://127.0.0.1:<port>`. Single-page app, dark and light themes, built for a projector (large type, high contrast). Real-time via WebSocket.

### Views
1. **Overview:** current mode, health strip (capture ok, daemon ok, model ok, notifier ok, dropped packets), top incidents within budget, noise meter, small traffic sparkline per top device.
2. **Incidents:** list + detail. Detail shows timeline, ATT&CK chain, evidence numbers, LLM summary (with "template fallback" badge when used), suggested response (dry run), and Approve/Dismiss buttons.
3. **Devices:** inventory table, type guess + confidence, vendor, first/last seen, trust level (trusted / unknown / quarantined), edit label, per-device drill-down with the three-window charts and peer comparison.
4. **Packets (Wireshark-style):** section 6.
5. **Rules:** two tabs, Detection and Enforcement (section 8). YAML editor with validation, a "test against last N minutes of traffic" button showing what it would have matched.
6. **Modes:** pick a monitoring mode, see exactly what it changes.
7. **Notifications:** configure channels, severity routing, quiet hours, send test message, delivery log with failures.
8. **Purple-team:** launch lab attacks, live results table.
9. **Settings and Audit log.**

### UI requirements
- Every string that originated on the network (hostnames, DNS names, HTTP hosts) is **untrusted**. Render with text-only APIs (`textContent`), never `innerHTML`. Set a strict Content-Security-Policy. This is a security product, so XSS via a poisoned hostname would be embarrassing. Add a test for it (hostname `<img src=x onerror=alert(1)>` must display as inert text).
- Empty states, loading states and error states for every view.
- Keyboard shortcuts for the Packets view (j/k to move, / to filter).
- Do not use external CDNs at runtime (offline lab). Vendor/bundle all JS, CSS and fonts locally.

## 6. Packet capture and display (Wireshark-like)

### Capture
- Capture filter uses BPF syntax (for example `host 192.168.2.3 and port 22`), configurable from GUI/CLI. Apply at capture time to reduce load.
- Maintain a **pcap ring buffer on disk** (size-capped, default a few hundred MB, oldest-first rotation). Needed for the Packets view, "capture export", and incident evidence.
- **Privacy defaults:** snaplen limits capture to headers by default (for example 96 bytes), so payloads are not stored. Full-payload capture is an explicit opt-in mode (Forensics, section 7) with a visible banner in the GUI, a retention limit, and an audit entry. Use only on networks you own or administer, and with the users' knowledge. State this in the README.
- Anything the LLM sees is still structured features only, regardless of capture mode. Raw packets never go to the LLM or to notification channels.

### Display
- **Packet list:** No., time, source, destination, protocol, length, info. Virtualized scrolling (handles tens of thousands of rows). Color rules by protocol/severity. Pause/resume live view.
- **Detail pane:** decoded layers as an expandable tree (Ethernet, IP, TCP/UDP, DNS, DHCP, ARP, ICMP, and TLS metadata such as SNI where visible).
- **Hex pane:** hex + ASCII for stored bytes. Selecting a field highlights its bytes (nice-to-have, P1).
- **Display filter bar:** a small filter language, similar in spirit to Wireshark's, for example `ip.src == 192.168.2.3 && tcp.dstport == 22`, `dns.qry.name contains "example"`, `proto == dns`. Implement as a simple parser to an AST evaluated over parsed packets. Show parse errors inline. Do not implement full Wireshark filter grammar.
- **Follow stream (P1):** reassemble a TCP flow and show it as text, only if payload capture is enabled.
- **Conversations table:** per host pair bytes/packets, sortable.
- **Click-through:** from an incident to the exact packets that caused it.
- **Export:** selected packets or time range to `.pcap` so users can open them in real Wireshark.
- Use dpkt or Scapy for decoding; consider a thin native `tcpdump`-to-pcap writer for performance. Verify throughput on the gateway Mac.

## 7. Monitoring modes

A mode is a named **config bundle** (detector sensitivity, capture depth, alert budget, notification behavior, enforcement policy). Switching modes is a single audited action.

| Mode | Purpose | Capture | Detection | Alerts | Enforcement |
|---|---|---|---|---|---|
| **Learning** | First day/session. Build baselines and inventory | headers only | rules + canary on, baseline detector off | none or digest only | off |
| **Standard** | Normal operation | headers only | all detectors, default thresholds | budgeted | dry-run suggestions |
| **Strict (lab/exam)** | College labs, exams | headers only | lower thresholds, new-device alerts always on, peer-group strict | higher budget, immediate for high severity | suggestions, optional TTL auto-apply for opted-in rules |
| **Quiet** | Busy office hours | headers only | high-confidence only | digest + critical only | off |
| **Forensics** | Investigating one host/incident | full payload for scoped filter, time-limited | unchanged | unchanged | off |
| **Maintenance** | Planned changes/patching windows | headers only | scoped suppression for listed hosts, time-boxed | reduced | off |
| **Replay** | Demo/testing from pcap | from file | as Standard | notifications disabled by default | off |
| **Air-gapped** | No external traffic at all | as Standard | as Standard | local only, all notifiers disabled | dry-run |

Rules for modes:
- Forensics and Maintenance require a scope (hosts) and an expiry. They revert automatically.
- Mode changes are written to the audit log and shown in the GUI header at all times.

## 8. Rule engine

Two separate rule systems. Keep them separate in code and UI so a typo in a detection rule can never block traffic.

### 8.1 Detection rules (YAML, Suricata/Sigma-inspired but simple)

```yaml
id: ssh-from-printer
name: Printer opening SSH connections
enabled: true
severity: 0.8
confidence: 0.9
technique: T1021          # verify ID
match:
  device_type: printer
  all:
    - proto: tcp
    - dst_port: 22
  window: 5m
  threshold:
    count: ">= 1"
    group_by: src_mac
action:
  alert: true
  notify: [slack]
```

Supported match fields: device_type, src/dst CIDR, ports, protocol, DNS name patterns, byte/packet counts, unique counts, rate over window, time-of-day, "destination never seen before". Operators: eq, in, cidr, regex (with length limit and timeout), gt/lt, group_by with threshold, `then` sequences within a time window (for simple chains).

Requirements:
- Schema validation with clear errors and line numbers.
- **Test mode:** run a rule against the last N minutes of stored flows and show matches, without alerting. This is the key usability feature.
- Rules shipped with sensible defaults for small-org threats (rogue DHCP, printer SSH, new device, student port scan, torrent/miner-like, DNS tunnel).
- Versioned: each edit keeps history, one-click rollback.

### 8.2 Enforcement rules (iptables-like), approval-gated

User asked for "custom rules like iptables". **macOS uses `pf`, not iptables.** Build an adapter interface:

```
class EnforcementBackend:
    def render(rule) -> str          # produce rule text
    def dry_run(rule) -> Result      # validate, no change
    def apply(rule) -> Result
    def remove(rule_id) -> Result
    def list_active() -> list
```
- **PfBackend (P0, macOS):** applies rules inside a dedicated pf **anchor** (for example `raven`) using `pfctl -a raven -f -`. Never flush or replace the main ruleset. **Verify:** Internet Sharing manages its own pf/NAT state on macOS, and incorrect pf changes can break the shared network. Test enable/disable of the anchor on the real setup before relying on it, and always keep a one-command "remove all Raven rules" (`raven enforce revoke --all`).
- **NftablesBackend / IptablesBackend (P2):** same interface for Linux gateways.

Rule format:
```yaml
id: quarantine-lab-pc-07
action: block               # block | allow | rate-limit(P2) | log
direction: both
match:
  src_mac: "aa:bb:cc:dd:ee:07"    # or src_ip, dst_ip, cidr, proto, port
ttl: 30m                     # required for block rules, auto-expires
reason: "incident 4f2a: port scan then brute force"
created_by: incident-4f2a
```

**Safety rules (non-negotiable):**
1. **Dry run is the default.** Every rule renders and validates first and shows exactly what will be applied.
2. **Human approval required** to apply, via GUI or CLI. No auto-apply except Strict mode rules the admin explicitly marked `auto_apply: true`, and those still require a TTL.
3. **Never-block safelist:** the gateway itself, the admin's machine, and any hosts listed in config can never be blocked. Reject such rules at validation time.
4. **Lockout protection:** refuse a rule that would cut the admin's current session (the IP/MAC used by the API client or CLI).
5. **TTL on every block**, with automatic expiry and removal. Default max TTL configurable.
6. **Rollback:** every applied rule can be revoked instantly, and a panic command removes all.
7. **Full audit entry** for each propose/approve/apply/expire/revoke.
8. **Blast-radius limit:** cap how many hosts can be blocked at once (default small). Mass-block requires an extra confirmation.
9. LLM text can suggest an action description, but the **rule text is generated by code from structured fields**, never from LLM output.

## 9. Notifications (Slack, Telegram, Discord)

External network calls exist only here. They are **opt-in**, off in Air-gapped and Replay modes, and the pitch must say "nothing leaves your network except the alert summaries you configure."

### Channels
- **Slack:** Incoming Webhook URL (simplest). Use Block Kit for a clean message: headline, severity, affected device, ATT&CK chain, suggested action, link to the incident in the GUI.
- **Discord:** Webhook URL, embed with color by severity.
- **Telegram:** Bot API `sendMessage` with `bot_token` and `chat_id` (HTML or MarkdownV2 parse mode with proper escaping).
- **Email (P2, optional).**

Verify each API's current payload format and rate limits against official documentation before implementing, since they change.

### Behavior
- **Severity routing:** for example critical to Telegram + Slack immediately, medium to Slack digest, low to daily digest.
- **Dedupe and grouping:** one message per incident, with updates grouped (edit or thread reply where the API supports it), not one per alert.
- **Rate limiting** per channel and global, **retry with exponential backoff**, **circuit breaker** after repeated failures, and a visible failure state in the GUI. A failing notifier must never block detection.
- **Quiet hours** with critical-only override, **daily digest** (top incidents, counts, noise reduction).
- **Test button / `raven notify test`** for each channel.
- **Delivery log** (channel, time, status, error) viewable in GUI.

### Security of notifications
- **Secrets** (webhook URLs, bot tokens) are never stored in the repo or plain `config.yaml`. Read from environment variables or the macOS Keychain; store only a reference in config. Redact in logs and API responses.
- **Message content is sanitized.** Only structured fields plus validated LLM text. No raw DNS names, hostnames or payloads from the network. Escape per-platform markup, since attacker-controlled text could otherwise inject links or mentions (for example `@everyone`). Disable mention parsing in Slack/Discord payloads.
- Messages contain the incident link and a short summary only. No packet data.
- **Two-way approval from chat (P2):** if built, only accept commands from allowlisted chat/user IDs, require a signed one-time token per action, and never allow enforcement apply from a chat message without the same safety rules as section 8.2. For the hackathon, links back to the GUI are enough.

## 10. Security of Raven itself

- Run API unprivileged, daemon minimal, socket permissions 0600.
- Auth token on all endpoints; constant-time compare; rate-limit auth failures.
- CSRF protection for any cookie-based GUI session (or use bearer-token-only).
- No external CDN or telemetry. Dependencies pinned in `requirements.txt`; run `pip-audit` if available.
- Treat every network-derived string as hostile in: UI (section 5), LLM input (original spec, section 11), notifications (section 9), logs (escape control characters), and rule matching (regex limits).
- Document the threat model in `README`: who the attacker is (a student, a compromised lab PC), what Raven does and does not protect against, and that it is a prioritization assistant, not an IPS.

## 13. Acceptance criteria additions

P0:
1. `raven doctor` reports green or gives actionable errors on a fresh Mac.
2. Daemon runs as root with a 0600 socket; API runs unprivileged; API rejects requests without the token.
3. CLI commands in the P0 list work and `--json` output parses.
4. GUI Overview, Incidents, Devices, Modes and Purple-team views work against live and replay data.
5. Packets view shows live packets, filters by host/port, exports a pcap that opens in Wireshark.
6. A poisoned hostname renders as inert text in the GUI and does not alter the LLM output or notification text.
7. One notification channel delivers a formatted incident message, respects severity routing, and a failing channel does not block detection.
8. Switching modes changes behavior as defined and is recorded in the audit log.
9. An enforcement rule proposal shows a dry run, requires approval, enforces TTL, rejects the safelist/lockout cases, and `revoke --all` works.
10. Original spec acceptance criteria still pass.
