Section numbers restart inside each part. A reference such as "section 11" means that section **within the same part** unless it names another part. Phrases like "this file" or "the original spec" inside a part mean that part, or Part 3 (the base specification), respectively.

**Instructions for Claude Code:** Read all six parts. Then follow Part 2 from Stage 0. Part 2 defines the order of work. Parts 3 to 5 define what is built. Part 6 defines how to stay accurate and applies at all times.

# PART 1: PRECEDENCE AND RESOLVED CONFLICTS

## Precedence

1. Part 5 (models) wins on anything about models, ML, embeddings, LLM slots, and model runtime.
2. Part 4 (V2) wins over Part 3 on architecture, interfaces, notifications, enforcement, packet capture, modes and rules.
3. Part 3 (base) supplies everything the later parts do not change.
4. Part 2 (working rules) wins on **order of work, quality bar and process**, over any time plan inside Parts 3 to 5.
5. Part 6 (execution protocol) applies to everything. If any statement in Parts 3 to 5 conflicts with what you verify on the real machine, verified reality wins and you record it in `docs/DECISIONS.md`.

If a conflict or ambiguity affects design and is not listed below, decide it, record one short entry in `docs/DECISIONS.md` (context, decision, reason), and continue.

## Resolved conflicts

| Topic | Earlier statement | Final decision |
|---|---|---|
| "Nothing leaves the machine" | Part 3: no external network calls | The only external calls are **opt-in alert notifications** (Slack, Telegram, Discord) and an **optional, off-by-default API model** for user-initiated deeper explanation. Both are disabled in Air-gapped and Replay modes. Pitch wording: "Nothing leaves your network except the alert summaries you choose to send." |
| Payload storage | Part 3: metadata only, no payloads | Default is **headers only** (short snaplen). Full-payload capture exists only as an opt-in Forensics mode, scoped to hosts, time-limited, with a banner, retention limit and audit entry. LLMs and notification channels still never see raw packets. |
| Enforcement | Part 3: suggestions only, never applied | Part 4 section 8.2 wins: rules can be applied **only** after human approval, with TTL, safelist, lockout protection, blast-radius limit and rollback. **P0 is dry-run only.** Real apply is P1 and only after the pf spike is confirmed by the human. Rule text is generated by code, never by an LLM. |
| Process model | Part 3: one gateway process | Part 4 wins: `sentineld` (root: capture, ring buffer, enforcement helper) and `sentinel-api` (unprivileged: detection, storage, LLM, notifications, web). |
| LLM | Part 3: one Ollama model | Part 5 wins: role-based slots (`explain`, `explain-lite`, `chat`, optional escalation) with Gemma 4 E2B as the default to be confirmed by benchmark. |
| DNS detection | Part 3: entropy and rules | Part 5 wins: rules plus an n-gram baseline, then an optional tiny char-CNN, combined in the ensemble. |
| Repository layout | Parts 3, 4, 5 each list directories | Use the **union**. Where names overlap (for example `explain/` vs `nlp/`, `detect/baseline.py` vs `ml/iforest.py`), Part 5's layout wins. The module diagram from Stage 0 is the final authority, and the architecture test enforces it. |
| Build order and time plan | Part 3: 10-hour phase table | Part 2's stage order wins (design docs, core, surround, polish). The Part 3 time table is a rough timebox guide only. |
| Priority tiers | Parts 4 and 5 each define P0/P1/P2 | **P0 is the union** of the P0 lists in Part 4 section 12 and Part 5 section 12. Same for P1 and P2. Never start P1 until P0 passes its acceptance criteria. |
| Pitch | Parts 3, 4, 5 each give one | Use this combined version: "Network security for places with no security team. It installs in minutes, learns every device, explains threats in plain English, alerts your admin on Slack, Telegram or Discord, and lets you drill into the exact packets. It is a team of small models, each doing one job, and each has to prove itself in our ablation table or it is switched off. It proposes firewall rules but never applies them without approval. It tests itself against real attacks and reports its own misses. Nothing leaves your network except the alert summaries you choose to send." |

## Non-negotiable properties (summary)

These hold in every part and win over convenience:

1. Only attack machines you own, on the closed lab network. Every attack script hard-checks the lab subnet.
2. No LLM makes a detection or enforcement decision.
3. Every network-derived string is hostile: it never reaches an LLM, notification, or UI unsanitized, and the UI renders it as inert text.
4. Enforcement is dry-run by default, human-approved, TTL-bound, safelisted, lockout-protected, auditable and revocable.
5. Capture never blocks: the event bus drops low-priority events and counts the drops.
6. Core before surround. No stubs, no unused code, no speculative abstraction.
7. Never claim a hardware result that was not observed. Hardware-dependent assumptions go to `docs/HUMAN_VERIFICATION.md`.
8. Every model earns its place in the ablation table or ships disabled.
